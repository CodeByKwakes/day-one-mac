# Set up contributor linting and Git hooks

Use this guide after cloning Day One Mac for development. It installs the
shared contributor tools, activates the Git hooks, and explains which checks
run at each point in the workflow.

These tools improve feedback before a pull request reaches continuous
integration. They do not replace the `Validate` GitHub Actions workflow.

## What the tooling provides

| Tool | Purpose |
|---|---|
| Husky | Connects the repository's versioned hooks to Git |
| commitlint | Requires Conventional Commit messages |
| lint-staged | Runs fast checks only against staged files before a commit |
| markdownlint-cli2 | Checks basic Markdown structure and whitespace |
| ShellCheck | Detects common shell-script errors |
| `scripts/validate.sh` | Runs the complete project-specific validation suite |

The Node dependencies are contributor-only. Day One Mac remains a shell-first
project, and the public installer does not ship `node_modules` or require these
packages at runtime.

## Hook behaviour

The committed hooks run at three different boundaries:

| Hook | Command | What it checks |
|---|---|---|
| `commit-msg` | `node_modules/.bin/commitlint --edit "$1"` | The proposed commit message follows Conventional Commits |
| `pre-commit` | `node_modules/.bin/lint-staged` | Staged shell and Markdown files pass their relevant linters |
| `pre-push` | `scripts/validate.sh` | The complete project validator passes before Git sends commits |

The pre-commit hook intentionally checks staged files rather than the entire
repository. The pre-push hook runs the broader project validator once the
change is ready to leave the machine.

The hooks call repository-local executables directly. They therefore use the
locked packages without depending on whichever global package-manager shim
happens to appear first on `PATH`.

## Prerequisites

From the repository root, confirm that Git, Node.js, pnpm, ShellCheck, and
ripgrep are available:

```bash
git --version
node --version
pnpm --version
shellcheck --version
rg --version
```

Use the Node version manager selected during Day One Mac setup. The contributor
package requires Node.js 22 or newer and pnpm 10 or newer.

On macOS, install missing non-Node tools with Homebrew:

```bash
brew install pnpm ripgrep shellcheck
```

Do not install Husky, commitlint, lint-staged, or markdownlint-cli2 globally.
The lockfile supplies the reviewed repository versions.

## 1. Install the locked dependencies

Run this command from the repository root:

```bash
pnpm install --frozen-lockfile
```

This command:

1. installs the versions recorded in `pnpm-lock.yaml`;
2. runs the `prepare` package script; and
3. tells Git to use the hooks under `.husky` for this checkout.

Use `pnpm install` without `--frozen-lockfile` only when intentionally changing
the contributor dependencies. Routine setup should never rewrite the lockfile.

## 2. Verify that Husky is active

Check the local Git hook path:

```bash
git config --local --get core.hooksPath
```

Expected output:

```text
.husky/_
```

List the project-owned hook entry points:

```bash
ls -1 .husky/commit-msg .husky/pre-commit .husky/pre-push
```

The `.husky/_` directory is generated by Husky and should not be edited. Make
changes only to the three project-owned hook files.

## 3. Test the commit-message rules

Test a valid message without creating a commit:

```bash
printf '%s\n' 'feat: add module health checks' | pnpm exec commitlint
```

The command should exit without output.

Now test an invalid message:

```bash
printf '%s\n' 'added some things' | pnpm exec commitlint
```

commitlint should report that the type and subject are missing.

The accepted types are:

```text
build, chore, ci, docs, feat, fix, perf, refactor, revert, style, test
```

The complete header can contain at most 100 characters. Use a body when the
reason or migration detail needs more space.

## 4. Run the linters directly

Run every configured linter:

```bash
pnpm run lint
```

Run one category while troubleshooting:

```bash
pnpm run lint:shell
pnpm run lint:markdown
```

Shell linting delegates to `scripts/lint.sh`, which runs ShellCheck with the
project's `.shellcheckrc`. Markdown linting checks the repository documentation
while excluding dependencies, agent skill files, and Obsidian template assets
whose literal spacing is part of their template format.

Run the complete project validator separately:

```bash
pnpm run validate
```

This is the same validator used by the pre-push hook and CI.

## 5. Use the hooks during normal work

Stage and review a focused change:

```bash
git add path/to/file
git diff --staged
```

Commit with a Conventional Commit message:

```bash
git commit -m "docs: add contributor tooling guide"
```

The sequence is:

1. lint-staged checks relevant staged files;
2. Git creates the proposed commit;
3. commitlint validates the commit message; and
4. Git finishes the commit only when both hooks pass.

When you push, the pre-push hook runs the complete validator:

```bash
git push -u origin docs/contributor-tooling
```

If validation fails, the push stops locally. Fix the reported problem, commit
the correction when necessary, and push again.

## What CI enforces

The `Validate` workflow independently:

- installs the locked contributor dependencies;
- checks a pull request title with commitlint;
- checks GitHub Actions workflows with actionlint;
- runs ShellCheck and markdownlint-cli2;
- checks shell syntax; and
- runs `scripts/validate.sh`.

CI checks the pull request title because Day One Mac uses squash merges. The
title normally becomes the Conventional Commit subject that Release Please
reads on `main`.

Passing local hooks does not guarantee that CI will pass. CI runs in a clean
environment and remains the merge gate.

## Bypass a hook only when necessary

Git permits a one-time bypass:

```bash
git commit --no-verify
git push --no-verify
```

Use `--no-verify` only when a hook itself is broken and the change is required
to repair it, or when an incident procedure explicitly requires the bypass.
Record the reason in the pull request.

A bypass does not disable CI. Do not use it to hide a lint, validation, or
commit-message failure.

To disable Husky temporarily for one command:

```bash
HUSKY=0 git commit -m "chore: repair contributor hooks"
```

Do not export `HUSKY=0` permanently in your shell configuration.

## Change or update the tooling

To update all contributor dependencies within the allowed version ranges:

```bash
pnpm update
pnpm run lint
pnpm run validate
```

To update one dependency deliberately:

```bash
pnpm update husky --latest
```

Review both `package.json` and `pnpm-lock.yaml`. Test all three hooks before
opening the pull request. Dependency updates should use a commit such as:

```text
chore: update contributor tooling
```

Do not hand-edit integrity values in `pnpm-lock.yaml`.

## Troubleshoot setup

### `pnpm install` cannot find Node or pnpm

Open a new terminal after completing the language-toolchain phase. Confirm that
the selected Node version manager initializes before pnpm is invoked. Avoid
initializing both fnm and NVM in the same shell.

### Git does not run the hooks

Reinstall the locked dependencies and inspect the hook path:

```bash
pnpm install --frozen-lockfile
git config --local --get core.hooksPath
```

If the path is not `.husky/_`, run:

```bash
pnpm run prepare
```

Then check whether another local Git tool is overwriting `core.hooksPath`.

### `pnpm` reports a package-manager version mismatch

The `packageManager` field records the reviewed pnpm version. Prefer activating
that version through Corepack or installing the matching Homebrew version. Do
not remove the field merely to suppress the warning.

If an old NVM/Corepack shim shadows the Homebrew-managed pnpm selected by Day
One Mac, inspect every candidate before changing `PATH`:

```bash
type -a pnpm
```

Keep one Node version manager and one pnpm owner. Do not initialize NVM and fnm
together.

### ShellCheck is missing

Install it and rerun the failed hook:

```bash
brew install shellcheck
pnpm run lint:shell
```

### Markdown lint fails on an intentional format

First determine whether the Markdown can be written more clearly without the
exception. If the syntax is generated or semantically significant, add the
narrowest possible exclusion to `.markdownlint-cli2.jsonc` and explain it in
the pull request. Do not disable a rule repository-wide for one avoidable line.

The root `CHANGELOG.md` is the existing exception. Release Please owns and
regenerates that file, and its section layout contains consecutive blank lines
that conflict with `MD012`. The linter therefore excludes only that generated
file. Do not edit the changelog by hand or disable `MD012` for authored
documentation.

### A valid-looking commit is rejected

Check for a missing colon, an unsupported type, an empty subject, or a header
longer than 100 characters:

```text
fix: resume interrupted database setup
```

See [Git workflow for Day One Mac](GIT-WORKFLOW.md) for version effects,
breaking-change syntax, branch names, and the release process.

## Completion checklist

- [ ] `pnpm install --frozen-lockfile` completes.
- [ ] `core.hooksPath` reports `.husky/_`.
- [ ] commitlint accepts a valid Conventional Commit.
- [ ] commitlint rejects an invalid message.
- [ ] `pnpm run lint` passes.
- [ ] `pnpm run validate` passes.
- [ ] The contributor understands that CI remains authoritative.
